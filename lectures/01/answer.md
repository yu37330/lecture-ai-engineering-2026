## 宿題

- 取り組んだレベル：**実装**
- やったこと：`app/ask.py` に `--chat` オプションを追加し、`client.chats.create(model=MODEL)` で作成した同一チャットセッションへ `chat.send_message()` で質問を連続送信する。従来の単発質問関数 `ask()` は維持した。`/exit` と `/quit` で終了、空入力は送信しない。入力・出力トークン数の表示処理も追加。
- 使ったモデル：**`gemini-3.5-flash-lite`**。単発質問と `lec01` の `--chat` モードの両方で実API応答を確認した。
- 結果：
  - **実測（`main`）**：`uv run pytest -q` で `11 passed in 3.71s`。ただし、これは `--chat` 追加前の `main` に対するテストである。
  - **実測（`main`）**：`uv run python -m app.ask --chat` は `error: unrecognized arguments: --chat`。作業ブランチが `main` だったため、追加機能はまだ存在していなかった。
  - **実測（`main`）**：講座固有の「3レベル」の質問にはGemini APIから回答が返った（上記演習欄参照）。
  - **実測（`lec01`）**：`uv run pytest -q` で **15 passed in 3.76s**。`uv run python -m app.ask --chat` の対話モードで、同じ起動プロセス中にGemini APIへ3回質問でき、各回の入力・出力トークン数が表示された。1回目の講座回数に関する質問には「どの講座か教えてください」と返答された。
  - **会話履歴の実API検証：成功**。2回目に「私の名前は田中です。覚えてください。」、3回目に「さっき伝えた私の名前は何ですか？」と質問したところ、3回目に「さっき教えていただいたお名前は、**田中さん**です！」と回答した。前ターンの情報を参照して回答できている。
  - **トークン数の実測**：1回目 **入力8 / 出力67**、2回目 **入力86 / 出力32**、3回目 **入力129 / 出力14**。入力トークン数の増加は、会話履歴が次の入力に含まれるチャット実装と整合している。ただしトークン数の増加だけで履歴保持を証明するものではなく、上記の実際の回答内容を根拠として判断する。
  - **終了処理**：`Ctrl+C` を入力して「会話を終了します。」が出力された。その後、`git pull --ff-only origin lec01` により当時のリモート最新コミット `842a0ea` を取り込めた。
- 気づき・疑問：LLMは講座固有の情報を知らないとき、一般論でそれらしい回答を生成する場合がある。一方、`--chat` では事前に伝えた名前を後続ターンで正しく利用できた。履歴を持つことで入力トークンが増えるため、長い会話ではコストや制限を考慮した履歴管理が必要。今回のセッションはPythonプロセス中に限られ、終了後に履歴を再利用する仕組みは実装していない。
